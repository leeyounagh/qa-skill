# 재시험 — 고친 화면이 정말 고쳐졌는지 실화면으로 다시 잰다

1 · 2차가 **새 결함을 찾는** 패스라면, 재시험은 **고쳤다는 티켓을 티켓 원문 기준으로 다시 재는** 패스다.
블라인드가 아니다 — 티켓 · PR 을 읽는다. 그래서 `PASS1-blind.md` · `PASS2-verify.md` 는 읽지 않는다.

이 파일에는 **도메인 값이 없다.** 트래커 · 상태 이름 · 판정하는 사람 · 댓글 형식 · 배포 확인법 · 로컬 실행법 ·
실행 에이전트 · 보조 스크립트 경로는 전부 **도메인 설정 파일의 「재시험」 절**(`SETUP.md` C절, 이하 「설정 C<n>」)에서 읽는다.

## 0. 재시험이 하지 않는 것

- **티켓 상태를 옮기지 않는다.** 통과 · 실패를 정하고 옮기는 사람은 설정 C3 이다. 재시험은 그 사람이 판단할
  **근거**를 만든다. 댓글에 「통과로 옮겨 주세요」 같은 상태 지시를 쓰지 않는다 — 정상/문제 사실만.
- **설정 C 절의 ● 칸이 비어 있으면 시작하지 않는다.** `SETUP.md` C절 온보딩부터 한다(시험 도중에 하나씩 묻지 않는다).
- **확인하지 않은 것을 PASS 로 적지 않는다.** 증거 없는 PASS 금지. 「아마 됐을 것」은 INCONCLUSIVE 다.
- **TEST 데이터를 묻지 않고 만들지 않는다**(설정 C10). 밖으로 나가는 동작(설정 C11)은 누르지 않는다.
- **범위 밖 발견으로 티켓을 만들지 않는다.** 판정서에 적어 사용자에게 넘긴다(통과를 막지도 않는다).

## 1. 자리 세 가지

| 자리 | 언제 | 어디서 | 결과가 가는 곳 |
|---|---|---|---|
| **[A] 사전 재시험** | 내 PR 의 티켓이 리뷰 · test 머지 단계 — 아직 테스트 서버에 없음 | 로컬 프론트 → 테스트 백엔드(설정 C8). C8 이 없으면 [A] 는 쓰지 않는다 | 내 PR 보완 · PR 본문 「머지 후 확인」. **트래커에 쓰지 않는다** |
| **[B] 확인 보조** | 설정 C2 「확인 대기」 상태 — 테스트 서버에 올라감 | 테스트 서버 | 근거 댓글 초안 → 사용자 승인 → 게시(설정 C4) |
| **[C] 재작업 재시험** | 「확인 실패」를 거쳐 다시 「확인 대기」에 온 티켓 | [B] 와 같음 | [B] 와 같음. 기준은 **지난 실패 조건** + 회귀 |

## 2. 트래커는 여섯 동작으로만 부른다

트래커가 무엇이든(이슈 트래커 · 저장소 이슈 · 문서 DB · 시트 · 없음), 절차는 아래 동작 이름만 쓴다.
동작마다 쓰는 도구 · 명령 틀은 설정 C1 에 있다. **「못 함」으로 등록된 동작은 오른쪽 대체 경로로 돈다.**

| 동작 | 쓰는 곳 | 못 할 때 대체 | 판정서에 남길 대가 |
|---|---|---|---|
| ① 확인 대기 목록 | 입력 고르기 | 사용자가 티켓 목록을 준다 | — |
| ② 본문 | 3) 계약 | 사용자가 본문을 붙여 넣는다 | 「기준 원천: 붙여 넣기(시각)」 — 첨부 · 링크가 빠졌을 수 있음 |
| ③ 댓글 | 3) 「확인 부탁」 · [C] 지난 실패 조건 | 붙여 넣기 + 「지난 실패 사유가 있나요?」 1문항 | [C] 조건 누락 가능 |
| ④ 상태 이력 | [C] 판별 | 제목 접두 · 라벨 · 사용자 답 | [C] 를 [B] 로 돌릴 수 있음 — 지난 PASS 까지 다시 재므로 느릴 뿐 틀리지 않음 |
| ⑤ 연결 PR | 2) 배포 확인 · 4) 회귀 확장 | `gh pr list --search "<티켓 ID>"` → 없으면 사용자가 PR 번호 | PR 없으면 「회귀 확장 없음」 경고 |
| ⑥ 결과 쓰기 · 이미지 | 7) 댓글 | **글로 출력** — 사용자가 붙인다. 캡처는 판정서 폴더 경로 | — |

- 티켓 ID 형식은 설정 C1 의 정규식을 쓴다(`ABC-123` · `#123` · 페이지 id 등).
- 판정서 머리에 **어느 동작이 대체로 돌았는지** 적는다 — 받는 사람이 판정의 강도를 안다.
- 재시험 중 처음으로 권한 거절이 나면 그 동작만 대체로 바꾸고 계속하고, 판정서에 적는다.

## 3. 절차

```
입력 ─▶ 설정 C 점검 ─▶ 2) 반영 확인 ─▶ 3) 계약 ─▶ 4) 회귀 확장 ─▶ ◆ 사용자 확인 ─▶ 5) 실행 ─▶ 6) 판정 ─▶ 7) 산출
```

### 1) 입력

| 입력 | 예 | 처리 |
|---|---|---|
| 티켓 ID 목록 | `재시험 ABC-12 ABC-40` | 그대로 |
| 확인 대기 필터 | `재시험 <도메인> 확인 대기 전부` | ① 동작으로 목록 → **보여 주고 고르게 한다**(전부 자동 실행 안 함). ④ 로 「확인 실패」 이력이 있으면 [C] 표시 |
| 사전 | `재시험 사전 #123` | [A]. PR 본문 · 제목의 티켓 ID 로 티켓을 찾고, 없으면 PR 본문 「확인 방법」이 기준 원천 |

### 2) 반영 확인 — 고쳐지지 않은 화면을 재지 않는다

- **[B] · [C]**: 티켓 상태가 설정 C2 「확인 대기」가 아니면 **BLOCKED(스왑 대기)** — 테스트 서버에서 재지 않는다.
  미리 보고 싶으면 [A] 를 안내한다.
- 상태가 「확인 대기」여도 ⑤ 로 연결 PR 을 모아 **설정 C7 배포 확인법**으로 한 번 교차 확인한다.
  상태는 사람이 옮기는 것이라 실제 배포와 어긋날 수 있다.
  - 하나라도 미반영 → **BLOCKED(상태와 배포 불일치)**. 사용자에게 보고만 한다. 상태를 되돌리거나 다른 사람에게 직접 알리지 않는다.
  - 확인법이 「사람에게 묻기」면 사용자에게 묻고 답을 판정서에 적는다.
  - 확인 도구가 실패하면 BLOCKED(반영 확인 불가). 「아마 반영됐을 것」으로 진행하지 않는다.
- **[A]**: 반영 확인 대신 로컬 프론트가 **어느 커밋**인지(브랜치 HEAD · 기준 브랜치) 판정서에 적는다. 백엔드도 바뀐 티켓이면
  테스트 백엔드에 새 백엔드가 올라갔는지만 확인하고, 아니면 백엔드 기준만 BLOCKED.
- 판정서 머리에 **시험한 빌드**(프론트 커밋 · 배포 시각)를 적는다.
- 상위(우산) 티켓은 하위가 전부 반영돼야 시작한다. 일부면 반영된 하위만 재고 상위는 판정 보류.

### 3) 계약 — 티켓 원문을 기준표로

틀은 `retest-contract.md`, 추출 규칙은 `scripts/ticket-to-criteria.md`. 절 이름 대응은 설정 C5.

- 기대 결과 항목 1개 = 기준 1개(`C1..Cn`). 재현 절차 = 시나리오. 확인 범위(계정 · 화면 · 폭) = 실행 조건.
- 댓글의 「확인 부탁」(어디서 / 필요한 것 / 절차 / 정상 / 문제)은 시나리오 · 기대 · **반증 조건**으로 1:1.
- 기획 결정 번호가 있으면 기대 결과의 정본은 그 결정이다.
- **[C]**: 지난 「확인 실패」 댓글의 조건(계정 · 폭 · 데이터까지)을 그대로 기준으로 옮기고, **지난번 PASS 기준은 다시 재지 않는다.**
- 기준마다 **측정 가능한 확인 방법**을 적는다 — 문구 일치 · 개수 · 요청 본문 · 측정기 0건 · 요소 캡처 열람.
  「자연스럽게」 「깔끔히」 같은 말은 측정 가능한 말로 바꾸거나 INCONCLUSIVE 예정으로 표시하고 게이트에서 확인받는다.
- **구현자 설명은 기대 결과에 넣지 않는다.** PR 본문의 「이렇게 고쳤다」는 4) 범위를 정하는 데만 쓴다.
- 절 이름이 안 맞는 옛 티켓은 「수정 방향」 등을 기대 결과로 쓰되 출처 칸에 **「추정 기준」**을 달고 게이트에서 확인받는다.
- 설정 C9 「없는 계정 조합」이 필요한 기준은 처음부터 「BLOCKED 예정」으로 적는다.

### 4) 회귀 확장 — 티켓이 적은 범위만 보면 통과하는 실패를 잡는다

실제 확인 실패의 대부분은 **평범한 데이터에선 되고 최악 데이터에서 깨진 것**, **고친 경로 말고 다른 경로가 그대로인 것**이었다.
⑤ 로 찾은 PR 의 바뀐 파일로 확장 기준(`X1..Xm`)을 만든다. 코드는 **기준 브랜치에서** 읽는다(`git show` · `git grep … <remote>/<branch>`) — 워킹트리 · 체크아웃 금지.

| 바뀐 것 | 확장 기준 |
|---|---|
| 화면 컴포넌트 | 그 컴포넌트를 그리는 **라우트 전부**. 데스크톱 ↔ 모바일 짝 화면(설정 B3 매핑표) |
| 공용 부품(설정 C13 공용 디렉터리) | 사용처 수를 센다. 2곳 이상이면 **PR 이 말하지 않은 사용처 2곳** |
| 서버 호출 · 서버 액션 · 미들웨어 | 같은 함수를 부르는 **다른 화면 · 다른 앱** |
| 표시 · 목록 · 표 기준 | 설정 C13 「최악 데이터 위치」 + `PASS1-blind.md` 축 ⑤ 표시 매트릭스 필수 칸(이 표만 참고 — 1차 하드룰은 해당 없음) |
| 지난 「확인 실패」 | 그 실패 조건은 **무조건** 다시 |

- 확장 기준은 **8개 상한.** 넘으면 진입점은 사용 빈도순(메뉴 > 바로가기 > 딥링크), 공용은 2곳. 잘린 것은 판정서 「안 본 것」.
- PR 이 아직 기준 브랜치에 없으면 확장은 머지된 diff 기준만. diff 가 너무 크면(파일 50+) 기준과 관련된 파일만 고르고 「확장 축소」 기록.
- 최악 데이터가 테스트 서버에 없으면 만들지 않고 그 X 를 BLOCKED(데이터 없음).

### ◆ 사용자 확인 게이트 (자동 승인에서도 묻는다)

기준표(C + X) · 쓸 계정 · 매트릭스 · 데이터 조작 여부를 한 화면으로 보여 주고 확인받는다.
「추정 기준」 · 「INCONCLUSIVE 예정」 · 데이터를 만들어야 하는 기준이 있으면 여기서 함께 묻는다.

### 5) 실행 — 새 컨텍스트의 실행기에 계약만 넘긴다

- 실행은 **서브에이전트**에 맡긴다. 종류는 설정 C15(없으면 범용 에이전트). 메인 세션은 3) · 4) 에서 PR 을 읽어 「고쳤겠지」 쪽으로 기울어 있다.
- **넘기는 것**: 기준표 · 테스트 서버(또는 [A] 로컬) 주소 · 계정 · 아래 측정 규칙 · **쓰기 금지 목록**(트래커 · 저장소 · 테스트 데이터 · 설정 C11).
  **넘기지 않는 것**: PR 설명 · 구현자 주장 · 이전 판정.
- 실행기는 끝에 **「쓴 것 없음」 자기점검**과 RESULT 블록(아래 7)을 낸다.

측정 규칙(실행기 프롬프트에 경로로 넣는다):

| 기준 성격 | 규칙 |
|---|---|
| 안내 · 토스트 · 확인창 | `PASS1-blind.md` 「측정 위생」(가)~(마) — 옵저버를 클릭 전에, 대화상자 0 확인, readonly 는 value |
| 표시 · 잘림 · 겹침 | `layout-probe.js` 0건 + 요소 캡처를 **열어 보고** 한 줄 서술 |
| 흔들림 · 레이아웃 이동 | 설정 C16 흔들림 측정 스크립트(있으면). 없으면 조작 전후 요소 위치 비교 |
| 저장 · 전송 내용 | `scripts/save-guard.js` — **저장 버튼 누르기 직전에만** 켠다(조회도 POST 인 앱이 있어 미리 켜면 화면이 빈다). 판독 뒤 새로고침으로 끈다 |
| 새로고침 없는 반영 | 조작 뒤 새로고침 **전** 한 번, **후** 한 번 — 따로 기록 |
| 권한 | 권한 있는 계정 · 없는 계정 둘 다. 계정을 바꿀 때마다 토큰 신원 확인(`PASS3-contract.md` 규칙) |
| 모바일 | `--browser webkit` 1회 추가. 실기기 전용(설치 앱 · 잠금 화면 · 하단 안전 영역)은 재지 않고 「실기기 확인 목록」으로 |

- 계정마다 세션을 따로(`-s=rt-<계정>`) 쓰고, 한 번 로그인한 상태를 저장해(`state-save`) 다시 쓴다. **끝나면 세션을 닫고 상태 파일을 지운다**(토큰이 들어 있다).
- 실제 저장 · 상태 변화가 기준이면(승인 · 발송) 게이트에서 허락받은 것만, 설정 C10 접두로 이름 붙여 만들고 끝에 지우거나 남은 것을 적는다.
- 테스트 서버가 내려가 있거나 5xx 가 이어지면 BLOCKED(환경). 10분 뒤 1회 다시.

### 6) 판정

기준마다 **PASS / FAIL / BLOCKED / INCONCLUSIVE**(해당 없으면 N/A). 티켓 판정은 **FAIL > BLOCKED > INCONCLUSIVE > PASS**.

- **PASS**: 기대 결과를 측정으로 확인했고, 시각 기준이면 캡처를 **열어 보고** 한 줄로 서술했다(「스크린샷 확인: …」).
  텍스트 스냅샷만으로 시각 기준을 PASS 하지 않는다 — 트리에 있어도 가려졌거나 화면 밖일 수 있다.
- **FAIL 확정 전 4단계** (`FALSE-POSITIVES.md` J항):
  1. 2회 재현 — 새 세션 · 캐시 비운 상태로 1회 더
  2. 미배포 아님 — 2) 다시 확인, 옛 빌드 청크가 아닌지(강력 새로고침)
  3. 계정 · 언어 · 권한 탓 아님 — 계약의 계정과 토큰 신원 일치
  4. 데이터 탓 아님 — 기준이 요구하는 데이터가 실제로 있었는지
- 해석이 들어간 FAIL(「기대를 이렇게 읽으면 실패」)만 반박 에이전트(설정 C15) 1회. 재현으로 바로 보이는 FAIL 은 반박 없이 확정.
- **X(회귀) FAIL**: 같은 PR 이 바꾼 파일 때문이면 원 티켓 FAIL. 원래부터 그랬으면(PR 이전 커밋에서도 재현) 「범위 밖 발견」.
- **범위 밖 발견**은 통과를 막지 않는다. 판정서 「범위 밖」 절에 1차 후보 형식으로 적어 다음 1차의 입력으로 넘긴다.
- 다시 재는 재재시험은 **이전 FAIL · BLOCKED 기준만.** 낮은 확신 · BLOCKED 를 「해소」로 바꾸지 않는다.

### 7) 산출

1. **재시험 판정서** — `<scratchpad>/retest-<날짜>.html`. 뼈대는 `verdict-template.html`, 형식은 `REPORT.md` 「재시험 판정서」.
   FAIL 기준 중 화면을 봐야 이해되는 것만 목업(`MOCKUP.md`).
2. **결과 댓글 초안** — `retest-comment.md` 틀 + 설정 C4(멘션 · 말투 · 요청 머리 · 날짜 · 캡처). [A] 는 만들지 않는다.
3. 사용자 승인 뒤 ⑥ 동작으로 게시. ⑥ 이 「못 함」이면 글로 출력.
4. **RESULT 블록**(맨 끝):

```result
verdict: PASS | FAIL | BLOCKED | INCONCLUSIVE   (티켓별)
evidence: 기준별 한 줄 — 측정값 · 캡처 열람 서술
fallbacks: 대체로 돈 트래커 동작
remaining: 안 본 것 · 실기기 확인 목록 · 테스트 서버 잔여   ← 비우면 「정말 남은 게 없다」는 선언
```

## 4. 마무리

- 세션 닫기 · 상태 파일 삭제 · 띄운 로컬 서버는 포트 → PID 로 종료.
- 만든 테스트 데이터는 지우고, 못 지운 것은 판정서 「테스트 서버 잔여」에.
- 이번에 확인된 「없는 계정 조합」 · 「대체로 돈 동작」은 설정 C 절에 반영할지 사용자에게 묻는다.
