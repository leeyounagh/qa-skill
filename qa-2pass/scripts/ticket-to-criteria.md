# 티켓 본문 → 기준표 추출 규칙

`RETEST.md` 3) 에서 쓴다. 절 이름은 팀마다 다르므로 **설정 C5 의 대응표**를 먼저 읽고, 아래 「뜻」으로 찾는다.
마크다운이 아닌 트래커(위키 문법 · 블록)는 받은 그대로 두고 절 이름만 찾는다 — 변환하지 않는다.

| 뜻 (설정 C5 키) | 흔한 절 이름 예 | 계약의 칸 | 추출 |
|---|---|---|---|
| `expected` 기대 결과 | 「이렇게 나와야 한다」 · Expected · Acceptance criteria · 「완료 조건」 · 표의 「지금 → 이렇게」 열 | 기대 | bullet · 번호 · 표 행 하나 = 기준 하나 |
| `steps` 재현 절차 | 「재현 방법」 · Steps to reproduce · 「확인 방법」 | 조작 | 번호 절차를 그대로. 계정 · 경로가 섞여 있으면 각 칸으로 |
| `scope` 확인 범위 | 「확인된 범위」 · Environment · 「영향 화면」 | 계정 · 화면 · 폭 · 언어 · 데이터 | 폭 · 계정 · 언어를 실행 조건으로. 「확인하지 않았다」고 적힌 조건은 **확장 후보**로 |
| `check_request` 확인 요청 댓글 | 「확인 부탁드립니다」 · 「검수 요청」 | 시나리오 · 기대 · **반증** | 「정상」 → 기대, 「문제」 → 반증 |
| `api_check` 서버 확인 | 「배포 후 개발자 확인」 · API · DB 확인 절 | 확인 방법(요청 · 응답 · DB) | 상태 코드 · 응답 키 · 행 수를 그대로 |
| `decision` 기획 결정 | 결정 번호(예: `D-123`) · 「PM 결정」 | 기대의 정본 | 본문과 결정이 다르면 **결정이 우선**, 출처에 둘 다 |
| `prior_failure` 지난 실패 | 「테스트 실패」 · 「확인 실패」 댓글 · 제목 접두 | [C] 기준 | 실패 조건(계정 · 폭 · 데이터)을 빠짐없이 |
| `fix_direction` 수정 방향 | 「수정 방향」 · 「고칠 방향」 | (기대가 없을 때만) 기대 | 출처 `추정 기준` — 게이트에서 확인 |

## 거르는 것

- **구현 설명**(「~를 ~로 바꿨다」, 파일 경로, 코드)은 기대에 넣지 않는다 — 회귀 확장(4)에서만 쓴다.
- **범위 밖이라고 적힌 것**(「이번에 하지 않은 것」 · 「별도 티켓」)은 기준에서 뺀다. 대신 판정서 「범위 밖으로 둔 것」에 그대로 옮긴다.
- **취소선 · 「→ 보류」** 항목은 뺀다.
- 같은 기대가 본문과 댓글에 두 번 있으면 하나로 합치고 출처를 둘 다 적는다.

## 온보딩에서 대응표 만들기 (설정 C5)

1. 확인 대기 티켓 1건 + 사용자가 고른 1~2건의 ② 본문 · ③ 댓글을 읽는다.
2. 위 표의 「뜻」마다 그 팀이 쓰는 절 이름을 찾아 후보로 적는다(없는 뜻은 「없음」).
3. 그 대응으로 기준표 초안을 만들어 보여 주고 「이렇게 읽는 게 맞나요?」. 고쳐진 대응을 설정 C5 에 적는다.
