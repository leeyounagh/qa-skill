# 3차 — API 계약 대조 (선택)

## 언제 도는가

**화면 QA 는 프론트 결함만 잡는다.** 프론트가 필수값·형식·권한 표시를 미리 막아 주기 때문에
백엔드 계약 위반은 1차 후보 목록에 오르지도 않는다. 백엔드 결함이 사는 곳은
**「프론트가 애초에 못 보내는 요청」** — enum 밖 값, 음수 페이지, 남의 employeeId, 미래 날짜,
상한 없는 limit, 프론트 게이트를 우회한 직접 호출이다.

3차는 블라인드가 아니다. 명세 부록(데이터 계약)을 펴 놓고 조항별로 때리는 것이 목적이다.

**이 패스를 못 도는 경우** — 명세에 API/DTO 부록이 없는 기능. 라우트·요청·검증 규칙을
스스로 추측해서 단언을 세우면 그건 QA 가 아니라 창작이다. 부록이 없으면 사용자에게
알리고 3차를 건너뛴다.

## 준비

### 1) 백엔드 주소

설정 파일의 FE 레포에서 읽는다. 앱별 `.env` 에 환경별 URL 이 있다.

```bash
grep -oE "https://[a-z0-9.-]+" <FE레포>/apps/<앱>/.env | sort -u
# NEXT_PUBLIC_API_<도메인>_URL_TEST 가 test 백엔드
```

⚠ 화면의 데이터 호출이 **서버 액션**(같은 URL 로 POST)이면 브라우저 네트워크 탭에 API 가
안 보인다. 그건 프론트가 서버 쪽에서 백엔드를 부르기 때문이고, 백엔드 자체는 대개 공개
앱서비스라 직접 호출된다.

### 2) 토큰 — **반드시 신원을 디코드해 확인한다**

```bash
playwright-cli -s=<세션> cookie-get token | grep -oE 'eyJ[A-Za-z0-9._-]+' > tok.txt
cut -d. -f2 tok.txt | tr '_-' '/+' | base64 -d | grep -oE '"(username|employeeId|userId)":("[^"]*"|[0-9]+)'
```

🔴 **이 확인을 건너뛰지 않는다.** `cookie-clear` 후 재로그인이 조용히 실패해 이전 계정 토큰이
그대로 남는 일이 실제로 있었다. 그걸 모르고 돌리면 「일반 계정이 남의 상세를
읽는다」 같은 **잘못된 고심각도 판정**이 나온다. 계정마다 **별도 브라우저 세션**을 쓰고,
프로브 직전에 payload 를 읽어 `username` 을 눈으로 확인한다.

### 3) 호출

```bash
curl -s -w "\nHTTP=%{http_code}\n" -H "Authorization: Bearer $T" "$BE/<경로>?<파라미터>"
```

날짜 파라미터는 **형식이 엔드포인트마다 다를 수 있다** — 한쪽은 `YYYY-MM-DD`, 다른 쪽은
RFC3339. 400 이 나오면 형식부터 의심한다.

⚠ **타임존을 섞지 않는다.** `…T23:59:59Z` 와 `…T23:59:59+09:00` 은 다른 창이다. 날짜 단위
필드를 시각까지 비교하는 API 면 경계에서 레코드가 빠진다 — 그것 자체가 관측거리다.

## 무엇을 때리는가

명세 부록의 각 줄이 그대로 단언이다. 아래는 축이고, 실제 항목은 부록에서 가져온다.

| 축 | 예 |
|---|---|
| **권한 게이트** | 작성자·승인자·참조자만 볼 수 있다는 조항 → 그 셋이 아닌 계정 토큰으로 상세를 직접 GET. 403 이 아니면 프론트 게이트만 있는 것이다 |
| **관리자 예외** | 명세가 침묵해도 코드에 관리자 우회가 있을 수 있다. 403 이 안 나오면 **그 계정이 관리자인지 먼저 확인**한다(관리자 명단 API) — 아니면 오탐이 된다 |
| **필수·enum** | 필수 누락, enum 밖 값. 파라미터마다 검증이 갈리는지 본다(한쪽은 400, 한쪽은 조용히 0건) |
| **경계값** | `limit=0`·`limit=99999`·`page=0`·`page=-1`. 조용히 클램프되는지, 상한이 있는지. **총건수가 작은 조직으로는 상한을 확인할 수 없다** — 큰 조직으로 재측정 |
| **중복·유일성** | 중복 방지 키가 명세대로 정규화되는지(날짜 단위 키에 시각을 다르게 넣어 두 번 생성 시도) |
| **클라 값 무시** | 「서버가 산출한다」고 적힌 필드에 남의 id 를 넣어 보낸다. 반영되면 대리 작성이 뚫린 것이다 |
| **목록 vs 상세 범위** | 목록에 어떤 필드까지 실리는지 본다. 상세가 막혀도 목록에 본문·개인정보가 실리면 게이트가 무의미하다 |

## 쓰기 프로브 — 승인과 원복

- **쓰기는 사용자 승인을 먼저 받는다.** 거절돼야 정상인 프로브도 성공하면 데이터가 남는다.
- **파괴적 프로브의 대상은 내가 만든 데이터여야 한다.** 남의 문서를 지워 보며 권한을 확인하지
  않는다 — 계정 A 로 만들고 계정 B 로 시도하는 형태로 바꾼다.
- 끝나면 `DELETE` 로 원복하고 **빈 상태를 조회해 확인**한다. 원복 경로가 없으면 보고서에
  「남아 있음 + 보정 방법」으로 명시한다.

## 판정

`PASS2-verify.md` 의 판정 규칙을 그대로 쓴다. 3차에만 해당하는 단서 둘.

- **계약대로 동작하는 것도 산출물이다.** 「조회 권한 403 정상 · 중복 방지 정규화 정상」처럼
  확인된 정상 동작을 판정서에 남긴다 — 다음 회차의 회귀 감시 대상이 된다.
- **명세에 없는 규칙이 코드 주석에 「확정 규칙」으로 있으면** 결함이 아니라 **명세 보완**이다
  (`FALSE-POSITIVES.md` F항). 조회 함수 이름이 아니라 쿼리 본문과 주석을 읽는다.

## 산출

2차 판정서에 합친다. 별도 문서를 만들지 않는다. 3차에서 나온 결함 · 기획확인도 **명세 대비 A / B1~B5** 를 붙여
판정서 맨 위 「명세 대비 요약」 표에 함께 센다(`PASS2-verify.md` 6) — 부록 계약 조항을 문언 그대로 어기면 A, 코드 주석에만 있는 규칙이면 B5).
다만 아래 두 절을 추가한다.

```markdown
### 기술 확인 대기
| 항목 | 내용 | 선행 조건 |
```
