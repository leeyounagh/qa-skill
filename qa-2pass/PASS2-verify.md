# 2차 — 명세·코드 대조와 오탐 필터

## 목적

1차 목록의 각 항목을 **결함 / 오탐 / 기획확인** 셋 중 하나로 떨어뜨린다.
「판단 못 함」으로 남는 항목이 0건이어야 2차가 끝난다.

시작 전에 `FALSE-POSITIVES.md` 를 읽는다.

## 입력 확인

| 모드 | 입력 |
|---|---|
| 1차에서 이어짐 | `pass1-raw-<날짜>.md` |
| 2차 단독 | 사용자가 준 파일·목록·티켓번호·QA 반려 목록 |
| 명세대조 | 명세 조항을 순서대로 훑어 항목을 만든다 (블라인드 아님) |

**입력이 남이 준 목록이면** — 실측 근거가 없다. 각 항목을 직접 재현해 실측을 붙일지 사용자에게 묻고,
재현하지 않은 항목은 판정서에 **「미재현」** 으로 표시한다. 실측 없이 「결함」으로 올리지 않는다.

## 절차

### 1) 명세 매핑

설정 파일 매핑표에서 그 기능의 명세를 찾아 읽는다. 매핑표에 없으면 사용자에게 위치를 묻고 **행을 추가**한다.

각 항목에 대해 적는다 — **명세 조항 번호 + 인용 문구**. 「명세에 있다/없다」만 적으면 근거가 안 된다.

- 명세가 그 동작을 **금지**하는가 → 결함 방향
- 명세가 그 동작을 **요구**하는가 → 오탐 방향
- 명세가 **침묵**하는가 → 대조군을 찾는다 (아래 2)

⚠ 명세 문서에는 **정본과 보관본이 따로 있을 수 있다.** 설정 매핑표가 가리키는 정본만 읽는다.
보관본(구 버전)을 읽으면 이미 반영된 변경을 결함으로 오판한다.

### 2) 코드 대조 — 배포 기준 브랜치에서만 읽는다

설정 파일의 레포 경로와 대조 기준 브랜치를 쓴다. 먼저 최신화한다.

```bash
git -C "<레포>" fetch <remote> <기준브랜치>
git -C "<레포>" show <remote>/<기준브랜치>:<파일 경로>
git -C "<레포>" grep -n "찾는 문자열" <remote>/<기준브랜치> -- <하위 경로>
```

**워킹트리 `cat`·`grep` 금지.** 현재 체크아웃된 브랜치를 보여줄 뿐이고, 그게 구시점 분기면
「가드가 아예 없다」고 오판한다. 프론트·백엔드 양쪽 다 같은 방식으로 본다.

판정에 직결되는 분기:

- 테스트 서버에서 재현되는데 **기준 브랜치에는 수정이 있으면 → 결함이 아니라 미배포다.** 종결.
- 기준 브랜치에도 그대로면 → 배포분에도 있다. 결함 방향.
- 티켓에 `경로:줄번호` 를 쓸 거면 **그 줄이 기준 브랜치에도 같은 번호인지** 확인한다.

**대조군을 찾는다.** 같은 제품 안에 같은 일을 하는 다른 화면이 있고 그쪽은 제대로 하면,
그게 「이렇게 나와야 한다」의 가장 강한 근거다. 명세가 침묵해도 대조군이 있으면 결함으로 세울 수 있다.
반대로 **음성 대조군**(다른 화면은 정상)은 결함 범위를 좁혀준다 — 전역 결함으로 확대하지 않게 해준다.

### 3) 이슈 트래커 중복 검색

설정 파일의 팀·프로젝트에서 증상 키워드로 검색한다.

- 같은 증상이 **열려 있으면** → 새로 만들지 않고 그 티켓에 코멘트로 붙인다
- 같은 증상이 **완료로 닫혀 있으면** → 재발이거나 미배포다. 어느 쪽인지 2) 로 판별한다
- 과거에 **오탐·기획의도로 종결됐으면** → 오탐. 그 티켓번호를 근거로 적는다

이미 티켓이 많이 쌓인 기능은 **공백 지대**(전용 티켓이 0건인 화면)를 먼저 파는 게 실익이 크다.

### 4) 오탐 체크리스트

`FALSE-POSITIVES.md` 를 항목마다 통과시킨다. 하나라도 걸리면 그 항목은 재측정 대상이다.

### 5) 판정

| 판정 | 조건 | 필수 기재 |
|---|---|---|
| **결함** | 명세 위반이 확정됐거나, 명세가 침묵하지만 **대조군이 존재**한다 | 명세 조항 또는 대조군 경로 · 기준 브랜치 확인 결과 · 재현율 |
| **오탐** | 명세·기존 티켓에 **기획의도 근거가 있다**. 또는 측정 실패였다. 또는 미배포였다 | **근거**(조항 번호 / 티켓번호 / 재측정 결과). 근거 없는 오탐 판정 금지 |
| **기획확인** | 명세가 침묵하고 대조군도 없다. 의도인지 결함인지 코드로 판별 불가 | 기획팀에 물을 **질문 문구**. 양쪽 답에 따른 처리 방향 |

**「기획확인」을 오탐으로 밀지 않는다.** 이게 2차에서 가장 흔한 사고다.
근거를 못 찾은 것과 기획의도인 것은 다르다. 근거가 없으면 「기획확인」이고, 사용자에게 묻는다.

**축 ① UX 불편은 명세로 판정되지 않는다.** 명세대로 동작해도 불편할 수 있다.
→ 명세와 일치하면 「기획확인」으로 두고, 「사용자 영향」 칸을 근거로 개선 제안인지 사용자에게 묻는다.
1차에서 이걸 잡는 게 이 스킬의 존재 이유이므로, 명세 일치를 이유로 조용히 버리지 않는다.

## 출력

`REPORT.md` 포맷으로 판정서를 만들어 사용자에게 보여준다.

- 「판단 못 함」 칸이 **0건**이어야 한다
- 오탐은 **지우지 않고 근거와 함께 남긴다** — 다음 QA 에서 같은 것을 다시 올리는 것을 막는다
- 기획확인 항목은 **문서 앞머리에 별도 섹션**으로 모은다 (기획이 먼저 봐야 하므로)

## 이슈 등록 — 승인 후에만

1. 판정서를 보여주고 **어느 항목을 올릴지** 사용자 승인을 받는다
2. 부모 이슈·담당자·우선순위를 묻는다
3. 팀에 이슈 작성 규칙 스킬이 있으면 **그것을 호출해** 따른다 — 작성 규칙을 여기에 다시 쓰지 않는다
4. 프론트·백엔드 결함은 **분리 등록**한다
5. 등록 후 이슈 URL 과 부모 구조를 사용자에게 돌려준다

## 마무리 — 원복과 기록

- 테스트 서버에 남긴 변경을 원복한다. **원복 경로가 없는 것**(삭제 수단이 없는 기록 등)은
  판정서에 「남아 있음 + 보정 방법」으로 명시한다
- 목 세션·주입 상태를 종료한다
- **재조사 금지 목록**을 만든다 — 이번에 오탐으로 확정한 것과 그 근거. 다음 QA 가 같은 길을 다시 걷지 않게.
