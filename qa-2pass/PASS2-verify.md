# 2차 — 명세·코드 대조와 오탐 필터

## 목적

1차 목록의 각 항목을 **결함 / 오탐 / 기획확인** 셋 중 하나로 떨어뜨린다.
「판단 못 함」으로 남는 항목이 0건이어야 2차가 끝난다.

시작 전에 `FALSE-POSITIVES.md` 를 읽는다.

## 입력 확인

| 모드 | 입력 |
|---|---|
| 1차에서 이어짐 | `pass1-raw-<날짜>.md` |
| 2차 단독 | 사용자가 준 파일·목록·티켓번호·QA 반려 목록 |
| 명세대조 | 명세 조항을 순서대로 훑어 항목을 만든다 (블라인드 아님) |

**입력이 남이 준 목록이면** — 실측 근거가 없다. 각 항목을 직접 재현해 실측을 붙일지 사용자에게 묻고,
재현하지 않은 항목은 판정서에 **「미재현」** 으로 표시한다. 실측 없이 「결함」으로 올리지 않는다.

## 절차

### 1) 명세 매핑

설정 파일 매핑표에서 그 기능의 명세를 찾아 읽는다. 매핑표에 없으면 사용자에게 위치를 묻고 **행을 추가**한다.

각 항목에 대해 적는다 — **명세 조항 번호 + 인용 문구**. 「명세에 있다/없다」만 적으면 근거가 안 된다.

- 명세가 그 동작을 **금지**하는가 → 결함 방향
- 명세가 그 동작을 **요구**하는가 → 오탐 방향
- 명세가 **침묵**하는가 → 대조군을 찾는다 (아래 2)

⚠ 명세 문서에는 **정본과 보관본이 따로 있을 수 있다.** 설정 매핑표가 가리키는 정본만 읽는다.
보관본(구 버전)을 읽으면 이미 반영된 변경을 결함으로 오판한다.

### 2) 코드 대조 — 배포 기준 브랜치에서만 읽는다

설정 파일의 레포 경로와 대조 기준 브랜치를 쓴다. 먼저 최신화한다.

```bash
git -C "<레포>" fetch <remote> <기준브랜치>
git -C "<레포>" show <remote>/<기준브랜치>:<파일 경로>
git -C "<레포>" grep -n "찾는 문자열" <remote>/<기준브랜치> -- <하위 경로>
```

**워킹트리 `cat`·`grep` 금지.** 현재 체크아웃된 브랜치를 보여줄 뿐이고, 그게 구시점 분기면
「가드가 아예 없다」고 오판한다. 프론트·백엔드 양쪽 다 같은 방식으로 본다.

판정에 직결되는 분기:

- 테스트 서버에서 재현되는데 **기준 브랜치에는 수정이 있으면 → 결함이 아니라 미배포다.** 종결.
- 기준 브랜치에도 그대로면 → 배포분에도 있다. 결함 방향.
- 티켓에 `경로:줄번호` 를 쓸 거면 **그 줄이 기준 브랜치에도 같은 번호인지** 확인한다.

**대조군을 찾는다.** 같은 제품 안에 같은 일을 하는 다른 화면이 있고 그쪽은 제대로 하면,
그게 「이렇게 나와야 한다」의 가장 강한 근거다. 명세가 침묵해도 대조군이 있으면 결함으로 세울 수 있다.
반대로 **음성 대조군**(다른 화면은 정상)은 결함 범위를 좁혀준다 — 전역 결함으로 확대하지 않게 해준다.

### 3) 이슈 트래커 중복 검색

설정 파일의 팀·프로젝트에서 증상 키워드로 검색한다.

- 같은 증상이 **열려 있으면** → 새로 만들지 않고 그 티켓에 코멘트로 붙인다
- 같은 증상이 **완료로 닫혀 있으면** → 재발이거나 미배포다. 어느 쪽인지 2) 로 판별한다
- 과거에 **오탐·기획의도로 종결됐으면** → 오탐. 그 티켓번호를 근거로 적는다

이미 티켓이 많이 쌓인 기능은 **공백 지대**(전용 티켓이 0건인 화면)를 먼저 파는 게 실익이 크다.

### 4) 오탐 체크리스트

`FALSE-POSITIVES.md` 를 항목마다 통과시킨다. 하나라도 걸리면 그 항목은 재측정 대상이다.

### 5) 판정

| 판정 | 조건 | 필수 기재 |
|---|---|---|
| **결함** | 명세 위반이 확정됐거나, 명세가 침묵하지만 **대조군이 존재**한다 | 명세 조항 또는 대조군 경로 · 기준 브랜치 확인 결과 · 재현율 |
| ↳ 단서 | **「명세 위반」은 구현 층을 전부 대조한 뒤에만 쓴다** — 존재하는 층(조회 쿼리 + 각 클라이언트)이 다 일관되면 결함이 아니라 **명세 정정**이다. `FALSE-POSITIVES.md` F항 | 층별 확인 결과 |
| **오탐** | 명세·기존 티켓에 **기획의도 근거가 있다**. 또는 측정 실패였다. 또는 미배포였다 | **근거**(조항 번호 / 티켓번호 / 재측정 결과). 근거 없는 오탐 판정 금지 |
| **기획확인** | 명세가 침묵하고 대조군도 없다. 의도인지 결함인지 코드로 판별 불가 | 기획팀에 물을 **질문 문구**. 양쪽 답에 따른 처리 방향 |

**「기획확인」을 오탐으로 밀지 않는다.** 이게 2차에서 가장 흔한 사고다.
근거를 못 찾은 것과 기획의도인 것은 다르다. 근거가 없으면 「기획확인」이고, 사용자에게 묻는다.

**축 ① UX 불편은 명세로 판정되지 않는다.** 명세대로 동작해도 불편할 수 있다.
→ 명세와 일치하면 「기획확인」으로 두고, 「사용자 영향」 칸을 근거로 개선 제안인지 사용자에게 묻는다.
1차에서 이걸 잡는 게 이 스킬의 존재 이유이므로, 명세 일치를 이유로 조용히 버리지 않는다.

**축 ⑤ 표시 깨짐은 「기획확인」 · 「UX 제안」으로 보내지 않는다.** 기능명세는 화면 폭 · 글자 잘림을 거의 적지 않는다.
그래서 명세 조항만 찾으면 표시 깨짐은 늘 B3 · B4 로 떨어지고, 그 사이 고쳐지지 않는다. 실제로 그랬다 —
1280 에서 버튼 글자가 음절 단위로 접히는 것은 「기획 확인」 질문으로 갔다가 1주 뒤 「결함」 답을 받았고,
검색 줄 버튼 떨어짐은 「화면 개선 제안」으로 묶였고, 열이 많은 표의 머리글 한 글자 잘림은 담당자 결정으로
취소됐다가 2주 뒤 윗선 결정으로 다시 열렸다.

판정 순서:

1. **표시 기준선**(설정 파일 도메인 「표시 기준선」)에 걸리는가 — 지원 폭 · 사이드바 상태 · 언어에서 지켜야 할 불변식.
   걸리면 **결함**이고, 근거 칸에 명세 조항 대신 **기준선 결정 번호와 인용**을 적는다. 6) 의 A 묶음 조건 ① 을 이것으로 채운다.
2. 기준선이 없어도 **같은 공용 부품을 쓰는 다른 화면이 같은 조건에서 멀쩡하면** 결함(B1 대조군).
3. 둘 다 없으면 기본은 **결함(B1, 근거: 측정 수치)** 이다. 「글자가 겹치거나 잘려 읽을 수 없다 · 누를 수 없다」는
   의도일 수가 없다. 기획에 묻는 것은 **고칠 모양**(말줄임 · 두 줄 · 배지 축약 · 칸 넓힘)이지 결함 여부가 아니다 —
   판정은 결함으로 두고 「디자인 선택」 질문을 따로 붙인다(예: 트리 이름 세로 꺾임 — 현상 · 안 A~D 표).
4. 기획 의도일 수 있는 것은 **밀도 · 여백 · 정렬 취향**뿐이다. 이것만 B4 로 보낸다.

**오탐 사유가 될 수 없는 것** — 아래는 판정서 「우회 방법」 칸에 적고 결함은 유지한다.

- 「원본(이관 전 화면)도 그렇다」 — 이관 전에는 데이터가 적어 안 보였을 수 있다. 파리티는 동작 기준이지 깨짐 기준이 아니다.
- 「창을 넓히면 / 사이드바를 접으면 / 열 폭을 끌어 넓히면 보인다」 — 지원 폭 안이면 결함이다.
- 「데이터가 비정상적으로 길다」 — 실제 운영 데이터에 있는 길이면 정상 입력이다. 1차가 고른 최악 데이터가 test 서버의 실데이터인지 확인한다.

코드 대조는 깨짐의 **원인 위치**(고정 폭 · `shrink-0` · viewport 미디어쿼리 · 폭 미지정 동적 열)를 찾아 티켓 개발 메모에
적는 용도다. 원인이 공용 부품(`packages/ui` 등)이면 **같은 부품을 쓰는 다른 화면**을 grep 해 영향 범위를 함께 적는다.

### 6) 명세 대비 명확성 — 결과를 두 묶음으로 가른다

판정 셋(결함·오탐·기획확인)과 **별개로**, 모든 항목에 「명세와 비교했을 때 명확한 결함인가」를 붙인다.
결과를 받는 사람(PM·개발)이 「바로 고칠 것」과 「판단이 필요한 것」을 한눈에 가르게 하려는 것이다.

| 묶음 | 들어가는 항목 | 조건 (전부 만족) |
|---|---|---|
| **A. 명확한 결함** | 판정이 「결함」이고 **명세 조항이 직접 금지 · 요구**하는 것 | ① 명세 조항 번호 + 인용 문구가 있다 ② 조항이 그 동작을 **문언 그대로** 금지 · 요구한다(해석 · 유추 없이) ③ 구현 층 대조를 마쳤고 층이 명세와 어긋난다(F항) ④ 기준 브랜치에도 그대로다 ⑤ 재현율이 실측돼 있다 |
| **B. 명확하지 않은 것** | 위 다섯 중 하나라도 빠진 결함, 그리고 「기획확인」 전부 | 아래 하위 유형 중 하나를 **반드시** 적는다 |

B 하위 유형 — 왜 명확하지 않은지를 적는다.

| 유형 | 뜻 | 처리 |
|---|---|---|
| B1 대조군 근거 | 명세는 침묵, 같은 제품의 다른 화면은 제대로 한다 | 결함으로 등록 가능 — 단 티켓에 「명세 근거 없음 · 대조군 근거」를 밝힌다 |
| B2 해석 필요 | 명세 문구가 있으나 이 상황에 적용되는지 해석이 필요하다 | 해석을 적고 기획에 확인 — 확인되면 A 로 올린다 |
| B3 명세 침묵 | 명세도 대조군도 없다(= 기획확인) | 기획 질문 문구 |
| B4 UX 개선 | 명세대로 동작하지만 사용자 영향이 있다 | 개선 제안 여부를 사용자에게 묻는다 |
| B5 명세 정정 후보 | 구현 층이 모두 일관되고 명세만 다르다(F항) | 결함이 아니라 명세 수정 제안 |

- **A 로 올리는 기준을 낮추지 않는다.** 「명세 취지상 당연하다」는 B2 다. 문언 인용이 없으면 A 가 아니다.
- 축 ⑤ 표시 깨짐은 **표시 기준선 결정의 인용**이 조건 ① 의 조항 인용을 대신한다(5) 참조). 층 대조(조건 ③)는
  해당 없음으로 적고, 대신 **처음 깨지는 폭**과 측정 수치를 조건 ⑤ 재현율 칸에 적는다.
- 오탐은 A·B 어디에도 넣지 않는다. 별도 절에 근거와 함께 남긴다.
- 1차 후보 수 = A + B + 오탐 이어야 한다. 합이 안 맞으면 빠진 항목을 찾는다.

## 출력

`REPORT.md` 포맷으로 판정서를 만들어 사용자에게 보여준다. 항목마다 **화면 예시가 필요한지** `MOCKUP.md` 1절로 가르고,
하나라도 필요하면 판정서를 HTML(`verdict-template.html`)로 내고 본문을 **페이지별**로 묶는다.

- 「판단 못 함」 칸이 **0건**이어야 한다
- 오탐은 **지우지 않고 근거와 함께 남긴다** — 다음 QA 에서 같은 것을 다시 올리는 것을 막는다
- 기획확인 항목은 **문서 앞머리에 별도 섹션**으로 모은다 (기획이 먼저 봐야 하므로)
- 판정서 맨 위에 **「명세 대비 요약」**(A 명확한 결함 N · B 명확하지 않음 N(유형별) · 오탐 N)을 둔다 — 6) 참조
- 사용자에게 보고할 때도 A 와 B 를 **나눠서** 말한다. 한 목록에 섞어 「결함 N건」으로만 보고하지 않는다

## 이슈 등록 — 승인 후에만

트래커는 도메인마다 다르다(Linear · GitHub Issues · Notion DB · Jira · 시트 · 없음). 등록은 **⑦ 등록 동작**으로만 부르고,
그 도구는 설정 C1 에 둔다(`SETUP.md` C1 표에 ⑦ 행을 더해 적는다. 재시험을 안 쓰는 도메인은 C1 의 이 행만 묻는다).
⑦ 이 「못 함」이거나 비어 있으면 **등록할 내용을 글(제목 · 본문 · 부모 · 담당자 제안)로 출력**하고 사용자가 옮긴다.

1. 판정서를 보여주고 **어느 항목을 올릴지** 사용자 승인을 받는다
2. 부모 이슈·담당자·우선순위를 묻는다
3. 팀에 이슈 작성 규칙 스킬이 있으면 **그것을 호출해** 따른다 — 작성 규칙을 여기에 다시 쓰지 않는다
4. 프론트·백엔드 결함은 **분리 등록**한다
4-1. 목업이 있는 항목은 목업 PNG 를 본문 「현상」 아래에 붙이고 캡션 문장을 그대로 쓴다(`MOCKUP.md` 3절)
5. 등록 후 이슈 URL 과 부모 구조를 사용자에게 돌려준다

## 마무리 — 원복과 기록

- 테스트 서버에 남긴 변경을 원복한다. **원복 경로가 없는 것**(삭제 수단이 없는 기록 등)은
  판정서에 「남아 있음 + 보정 방법」으로 명시한다
- 목 세션·주입 상태를 종료한다
- **재조사 금지 목록**을 만든다 — 이번에 오탐으로 확정한 것과 그 근거. 다음 QA 가 같은 길을 다시 걷지 않게.
