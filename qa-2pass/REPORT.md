# 산출물 포맷

## 1차 — `pass1-raw-<날짜>.md` (스크래치패드)

머리말에 스윕 조건을 남긴다. 나중에 범위를 되짚을 근거다.

```markdown
# 1차 블라인드 QA — <기능> / <탭> · <날짜>
- 테스트 서버 빌드 시점: <확인한 값 또는 "미확인">
- 계정: <등급별 목록>
- 훑은 화면: 목록 / 등록 모달 / 상세 / 삭제
- 안 본 것: <이유와 함께>
```

항목은 하나씩 **원인 칸 없이** 적는다.

```markdown
## P1-07
| | |
|---|---|
| 축 | ④ 기능 완성도 |
| 화면 | <기능> > <탭> |
| 계정 | 일부 권한 계정 |
| 조작 | 시작 18:00 / 종료 09:00 입력 후 저장 |
| 관찰 | 저장됨. 리로드 후 유지. 경고 0건 (옵저버 확인, 같은 세션 다른 토스트는 포착됨) |
| 재현 | 3회 중 3회 |
| 스크린샷 | shot-p1-07.png |
| 사용자 영향 | 잘못된 기록이 남고 화면에서 지울 수단이 안 보인다 |
```

`사용자 영향` 은 반드시 채운다 — 2차에서 「기획의도」로 판정돼도 이 칸이 있으면 UX 개선 제안으로 남는다.

### 축 ② 는 표로 따로

```markdown
## 계정 교차 비교 — <화면>
| 관측점 | 최고권한 | 일부권한 | 일반 | 권한 무관? | 일치? |
|---|---|---|---|---|---|
| 총 건수 | 53 | 53 | 12 | 아니오(본인분) | — |
| 조직 합계 | 690 | 688 | 690 | 예 | **불일치** |
```

## 2차 — 판정서

**기획확인을 맨 앞에 둔다.** 기획이 먼저 봐야 하고, 개발 판단을 기다리게 하면 안 된다.

```markdown
# <기능> QA 판정서 — <날짜>
결함 N · 오탐 N · 기획확인 N   (1차 후보 N건)

## 기획 확인 필요 — 먼저 답이 필요한 것
### Q1. <한 줄 질문>
- 현재 동작: <실측>
- 명세: <조항 번호 + 인용, 또는 "침묵">
- 답에 따른 처리: 의도다 → 명세 보완 / 아니다 → 결함 등록

## 결함
### D1. <증상 한 줄 — 비개발자가 읽는 문장>
| | |
|---|---|
| 1차 항목 | P1-07 |
| 재현율 | 3/3 |
| 명세 근거 | 1.4.2 「종료는 시작 이후여야 한다」 |
| 대조군 | <있으면 경로> |
| 기준 브랜치 | 그대로 있음 (`<파일>:41`) → 배포분에도 있다 |
| 영향 | <사용자 영향> |
| 담당 | 프론트 / 백엔드 |

## 오탐 — 근거와 함께 남긴다 (다시 올리지 말 것)
| 1차 항목 | 증상 | 오탐 근거 |
|---|---|---|
| P1-03 | 관리 화면이 열린다 | 메뉴 단위 권한. <티켓번호> 기획의도 확정 |
| P1-11 | 저장 실패 안내 없음 | 재측정 시 「…를 입력해 주세요.」 정상 출력 (측정 실패) |

## 테스트 서버 잔여
| 무엇 | 원복 | 보정 방법 |
|---|---|---|

## 미검증 (이유)
```

판정서는 사용자 검토용이다. 항목이 많거나 스크린샷을 붙일 거면 브라우저에서 보는 형태로 렌더한다.

## 「판단 못 함」은 남기지 않는다

결함·오탐·기획확인 셋 중 하나로 못 떨어뜨린 항목이 있으면 **판정서를 내지 않는다.**
근거가 부족하면 그건 「기획확인」이고, 측정이 부족하면 재측정한다.
